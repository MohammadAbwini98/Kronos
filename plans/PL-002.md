| Field | Value |

## 1. System Architecture

### 1.1 Architecture Style

The system SHALL remain a local, modular monolith composed of multiple Python worker processes coordinated by a PowerShell supervisor. It is not a distributed microservice deployment. The architecture SHALL use PostgreSQL as the system of record and local files as secondary artifacts for CSV, JSON, HTML reports, logs, and model assets.

| Component | Runtime | Responsibility |
|---|---|---|
| Dashboard frontend | Browser, static HTML/JS served by Python HTTP server | Operator UI, charts, status views, model performance views, signal audit views |
| Dashboard backend | `src/dashboard_server.py` | REST API, subprocess orchestration, file serving, status aggregation |
| Prediction scheduler | `src/main_prediction_scheduler.py` | Periodic latest-data fetch and active model prediction |
| WebSocket stream worker | `src/main_stream_ohlc.py` | Live quote/candle ingestion |
| Validation worker | `src/main_validation_worker.py` | Actual candle fetch, forecast scoring, active/shadow status updates |
| Auto-finetune worker | `src/main_auto_finetune_worker.py` | Dataset preparation, training command orchestration, candidate status |
| Maintenance worker | `src/main_maintenance_worker.py` | Historical backfill, archives, backups, cleanup |
| Scoring module | New `src/forecast_scoring.py` | Canonical forecast, horizon, signal, and shadow scoring |
| Feature pipeline | New `src/feature_engineering.py` | Deterministic feature generation |
| Experiment/backtest pipeline | New `src/walk_forward.py` and related CLI | Walk-forward evaluation and cached backtest runs |
| PostgreSQL | Local or configured remote PostgreSQL | Canonical data, forecasts, outcomes, model versions, metrics |
| File artifacts | `output/` | CSV inputs/forecasts, validation reports, logs, backups, model status files |
| Capital.com REST API | External HTTPS API | Auth, market metadata, historical/actual candles |
| Capital.com WebSocket API | External WebSocket | Live quote/OHLC stream |
| Kronos runtime | Local Python runtime and model folders | Forecast inference |

### 1.2 High-Level Data Flow

1. `start_dashboard.ps1` loads `.env`, applies migrations, starts dashboard and workers.
2. WebSocket and REST workers persist OHLCV candles into `ohlcv_candles`.
3. Prediction scheduler fetches latest candles, creates a Kronos input CSV, runs active model inference, writes `prediction_runs`, `forecast_candles`, `signals`, and metadata artifacts.
4. If a pending-review candidate exists, shadow inference runs on the same input window and stores `signal_shadow_predictions`.
5. Validation worker fetches actual candles after forecast timestamps are due, writes `prediction_outcomes`, signal status, shadow status, and horizon metrics.
6. Scoring module is the single implementation used by DB updates, JSON validation reports, shadow evaluation, backtesting, and dashboard metrics.
7. Auto-finetune worker creates dataset snapshots, runs configured training, registers `model_versions`, and assigns promotion status using multi-gate evaluation.
8. Dashboard API reads PostgreSQL and artifacts to render status, signal table, model performance, data quality, backtests, and audit trail.

### 1.3 Process and Ownership Boundaries

| Process | Reads | Writes | Must not do |
|---|---|---|---|
| Dashboard server | PostgreSQL, `output/`, request payloads | reports, optional prediction subprocess output | Direct trading calls |
| Scheduler | Capital.com REST, PostgreSQL, model status | prediction runs, signals, forecasts, shadow predictions | Train models |
| Validation worker | Capital.com REST, PostgreSQL, forecast artifacts | outcomes, metrics, signal statuses | Modify model files |
| Auto-finetune worker | PostgreSQL, dataset snapshots, command output | model version rows, status file, dataset CSVs | Promote without gates |
| Maintenance worker | PostgreSQL, Capital.com REST, `output/` | backfill rows, archives, backups | Delete unarchived active data |
| WebSocket worker | Capital.com WebSocket | live quotes, OHLCV candles, raw events | Run predictions |

### 1.4 Supervisor Requirements

- The supervisor SHALL create a unique `supervisor_instance_id` at startup.
- The supervisor SHALL acquire a PostgreSQL lease or lock file before starting workers.
- If another active supervisor exists and `ALLOW_DUPLICATE_WORKERS` is not true, startup SHALL fail with a clear message.
- Each worker heartbeat SHALL include `supervisor_instance_id`, PID, worker name, and command fingerprint.
- Duplicate worker detection SHALL be exposed through `/api/status`.

### 1.5 Architectural Constraints

- The system SHALL not call Capital.com trading endpoints such as `/positions`, `/orders`, `/workingorders`, or `/confirms`.
- All timestamp persistence SHALL use UTC `TIMESTAMPTZ`.
- UI display MAY convert to `CAPITAL_DISPLAY_TIMEZONE`.
- PostgreSQL is the canonical store for metrics and statuses.
- File artifacts SHALL be reproducible outputs, not the only source of canonical state.
- Candidate model approval SHALL never be based only on artifact existence.

## 3. API Contracts

All dashboard API responses SHALL be JSON. All error responses SHALL use the standard error envelope defined in section 7.1.

### 3.4 Prediction API

#### `POST /api/predict`

Runs an on-demand prediction for selected input. This endpoint SHALL validate all input server-side.

Request:

```json
{
  "market": "ETHUSD",
  "symbol": "ETHUSD",
  "resolution": "MINUTE_5",
  "pred_len": 12,
  "lookback": 512,
```

## 4. Functional Requirements

### 4.1 Canonical Scoring

| ID | Requirement |
|---|---|
| FR-SCORE-001 | The system SHALL implement `src/forecast_scoring.py` as the only source of truth for direction, horizon, signal, and cost-aware scoring. |
| FR-SCORE-002 | The first forecast candle direction SHALL be compared against `last_input_close`. |
| FR-SCORE-003 | Subsequent forecast candle directions SHALL be compared forecast-close to prior forecast-close. |
| FR-SCORE-004 | Actual directions SHALL be compared actual-close to prior actual-close, with the first actual direction anchored to `last_input_close`. |
| FR-SCORE-005 | If absolute move percent is below `flat_threshold_pct`, direction SHALL be `FLAT`. |
| FR-SCORE-006 | Per-horizon outcomes SHALL be `WIN` when predicted direction equals actual direction, `LOSS` when they differ, and `PENDING` when actual candle is unavailable. |
| FR-SCORE-007 | Signal-level status SHALL be `PENDING` when zero horizons are validated, `WIN` when wins are greater than or equal to losses, and `LOSS` otherwise. |
| FR-SCORE-008 | JSON quality reports, DB outcomes, horizon metrics, and shadow metrics SHALL use the same scoring version. |

### 4.2 Horizon Metrics

| ID | Requirement |
|---|---|
| FR-HORIZON-001 | Validation SHALL upsert one `forecast_horizon_metrics` row per forecast candle. |
| FR-HORIZON-002 | Dashboard SHALL aggregate metrics by horizon index. |
| FR-HORIZON-003 | Promotion gates SHALL be able to require pass thresholds for configured horizon groups, for example horizons 1-3. |

### 4.3 Cost-Aware Signal Scoring

| ID | Requirement |
|---|---|
| FR-SIGNAL-001 | A signal SHALL be actionable when `signal IN ('LONG','SHORT')`. |
| FR-SIGNAL-002 | `movement_after_cost_pct` SHALL equal realized move in predicted direction minus `cost_threshold_pct`. |
| FR-SIGNAL-003 | Actionable precision SHALL be calculated separately from HOLD status. |
| FR-SIGNAL-004 | HOLD quality SHALL be `GOOD_HOLD` when realized absolute move remains below cost threshold and `MISSED_MOVE` otherwise. |

### 4.4 Data Quality Gate

| ID | Requirement |
|---|---|
| FR-DQ-001 | Before prediction, the scheduler SHALL compute a data quality report for the lookback window. |
| FR-DQ-002 | The report SHALL persist to `prediction_run_quality` and prediction metadata JSON. |
| FR-DQ-003 | If quality grade is below configured `MIN_PREDICTION_QUALITY_GRADE`, the scheduler SHALL either block prediction or mark the signal confidence as downgraded according to configuration. |
| FR-DQ-004 | Shadow evaluation and promotion metrics SHALL support filtering out runs below a configured quality grade. |

### 4.5 Feature Engineering

| ID | Requirement |
|---|---|
| FR-FEAT-001 | Feature generation SHALL be deterministic for a given candle set and `feature_set_id`. |
| FR-FEAT-002 | Feature generation SHALL not mutate canonical OHLCV candles. |
| FR-FEAT-003 | Features SHALL be stored in `ohlcv_features` and linked by `candle_id`. |
| FR-FEAT-004 | Missing values in rolling features SHALL be represented as SQL `NULL` until enough lookback exists. |

### 4.6 Dataset Snapshots

| ID | Requirement |
|---|---|
| FR-DATASET-001 | Training, validation, shadow evaluation, promotion evaluation, and backtest datasets SHALL be registered in `dataset_snapshots`. |
| FR-DATASET-002 | Dataset snapshots SHALL include a checksum over ordered rows and configuration. |
| FR-DATASET-003 | Promotion SHALL fail if training and promotion evaluation windows overlap. |
| FR-DATASET-004 | Auto-finetune status SHALL display training dataset id and evaluation dataset id. |

### 4.7 Shadow Mode

| ID | Requirement |
|---|---|
| FR-SHADOW-001 | A shadow prediction SHALL run on the same input window as the active prediction. |
| FR-SHADOW-002 | Shadow predictions SHALL not insert rows into `prediction_runs` as active runs unless role is explicitly `shadow` in `run_model_versions`. |
| FR-SHADOW-003 | Shadow predictions SHALL be tied to `model_versions.model_version_id`. |
| FR-SHADOW-004 | Shadow status SHALL update to `WIN`, `LOSS`, or `PENDING` using canonical scoring. |
| FR-SHADOW-005 | Dashboard SHALL show active signal/status and shadow signal/status in the same row. |

### 4.8 Promotion Gates

| ID | Requirement |
|---|---|
| FR-PROMO-001 | Promotion evaluation SHALL write one `promotion_gate_results` row per gate. |
| FR-PROMO-002 | A model SHALL be `approved` only when all required gates are `PASS`. |
| FR-PROMO-003 | Required gates SHALL include minimum shadow samples, direction accuracy, lift over active, actionable precision, horizon performance, MAPE/RMSE regression tolerance, baseline beat rate, and data quality coverage. |
| FR-PROMO-004 | A rejected candidate SHALL retain its metrics and rejection reason. |
| FR-PROMO-005 | Production selection SHALL use only `promoted` model versions with complete artifacts. |

### 4.9 Walk-Forward Backtesting

| ID | Requirement |
|---|---|
| FR-WF-001 | Walk-forward experiments SHALL use only candles prior to the forecast window as input. |
| FR-WF-002 | Experiments SHALL support forecast cache keys to avoid duplicate inference. |
| FR-WF-003 | Results SHALL compare candidate, active, and baseline models over identical windows. |
| FR-WF-004 | Backtest metrics SHALL be persisted in `walk_forward_results.metrics`. |

### 4.10 Duplicate Worker Prevention

| ID | Requirement |
|---|---|
| FR-OPS-001 | Supervisor startup SHALL acquire `supervisor_leases.lease_name='dashboard_stack'`. |
| FR-OPS-002 | Startup SHALL fail when a non-expired lease exists and duplicate workers are not explicitly allowed. |
| FR-OPS-003 | Lease heartbeat SHALL refresh at least every 30 seconds. |
| FR-OPS-004 | Workers SHALL include supervisor id in heartbeat details. |

### 4.11 API Rate-Limit Cooldown

| ID | Requirement |
|---|---|
| FR-RATE-001 | REST client SHALL classify requests by endpoint class. |
| FR-RATE-002 | On HTTP `429`, the endpoint class SHALL enter `COOLDOWN`. |
| FR-RATE-003 | Workers SHALL skip affected work during cooldown and write heartbeat status `COOLDOWN`, not `ERROR`. |
| FR-RATE-004 | Dashboard SHALL show cooldown reason and retry time. |

### 4.12 Dashboard Reporting

| ID | Requirement |
|---|---|
| FR-UI-001 | Dashboard SHALL include a model performance tab. |
| FR-UI-002 | Dashboard SHALL include a signal audit view accessible from each signal row. |
| FR-UI-003 | All POST action failures SHALL be shown as failures when `response.ok` is false. |
| FR-UI-004 | Fetch actuals, validate actuals, and baselines SHALL operate on the selected run id, not implicit latest metadata. |

## 5. Non-Functional Requirements

### 5.1 Performance

| Area | Requirement |
|---|---|
| Status API | `GET /api/status` p95 latency under 500 ms with 10,000 runs and 120 recent candles |
| Signals API | `GET /api/signals` p95 latency under 750 ms with 100,000 signals using indexes |
| Model performance API | p95 latency under 1500 ms for a 90-day window after aggregation indexes exist |
| Validation scoring | Score 1,000 forecast candles in under 2 seconds excluding external fetch time |
| Feature generation | Generate features for 50,000 candles in under 30 seconds on local machine |
| Dashboard refresh | Default polling interval SHALL be no lower than 5 seconds |
| Prediction latency | Signal SHALL be saved within 90 seconds after a candle boundary under normal local model runtime |

### 5.2 Scalability

- PostgreSQL schema SHALL support at least:
  - 10 million OHLCV candles,
  - 1 million forecast candles,
  - 1 million prediction outcomes,
  - 100,000 signals,
  - 10,000 shadow evaluations.
- Archive jobs SHALL not block current prediction or validation writes.
- Long-running backtests SHALL run asynchronously or as worker jobs, not on the HTTP request thread.

### 5.3 Concurrency

- Only one active scheduler per symbol/resolution SHOULD run unless explicitly configured.
- Database writes SHALL use idempotent upserts keyed by run id, horizon index, dataset id, and model version id.
- Worker leases SHALL prevent duplicate process stacks.
- Validation SHALL tolerate partial actual availability and SHALL be repeatable.

### 5.4 Security

- Capital.com credentials SHALL be read from environment variables or `.env`; they SHALL not be logged.
- API responses SHALL not expose secrets or full auth headers.
- The backend SHALL reject any path attempting to call trading endpoints.
- Dashboard POST APIs SHALL validate inputs server-side.
- If remote access is enabled, the dashboard SHALL require authentication. Acceptable local implementation:
  - static bearer token from env `DASHBOARD_API_TOKEN`, or
  - local-only binding to `127.0.0.1`.
- Fine-tune command execution SHALL avoid `shell=True` where practical. If retained, command templates SHALL be validated and logged with sensitive values redacted.

### 5.5 Data Persistence

- All migrations SHALL be idempotent.
- Each canonical record SHALL include `created_at` and/or `updated_at` where operationally useful.
- Dataset snapshots and model versions SHALL be immutable except status and metrics fields.
- Backups SHALL include database dumps or exportable CSV/JSON for new tables.

### 5.6 Reliability

- Workers SHALL write heartbeat at least every 60 seconds during long sleep or long work.
- A stale heartbeat threshold SHALL be configurable. Default: 180 seconds.
- `ERROR` SHALL indicate active failure. `COOLDOWN` SHALL indicate intentional pause after external rate limits.
- HTTP 429 from Capital.com SHALL not cause tight retry loops.

## 7. Error Handling & Logging

### 7.1 Standard Error Response

All API errors SHALL return:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid request payload",
    "details": {
      "field": "resolution",
      "reason": "Unsupported resolution"
    },
    "request_id": "uuid",
    "timestamp_utc": "2026-05-01T00:00:00Z"
  }
}
```

Error code set:

| Code | HTTP | Meaning |
|---|---:|---|
| `VALIDATION_ERROR` | 400 | Invalid request payload or query |
| `NOT_FOUND` | 404 | Run, dataset, or model version not found |
| `CONFLICT` | 409 | Duplicate job, duplicate supervisor, invalid state transition |
| `RATE_LIMIT_COOLDOWN` | 429 | Local endpoint class is cooling down |
| `EXTERNAL_API_ERROR` | 502 | Capital.com error |
| `MODEL_RUNTIME_ERROR` | 500 | Kronos subprocess/import failed |
| `DATABASE_ERROR` | 503 | PostgreSQL unavailable |
| `INTERNAL_ERROR` | 500 | Unhandled server error |

### 7.2 Logging Requirements

All logs SHALL include:

- timestamp,
- service name,
- log level,
- event name,
- request id or run id when available,
- symbol and resolution when applicable,
- exception stack trace for failures.

Critical events to log:

| Event | Level | Required fields |
|---|---|---|
| Supervisor lease acquired | INFO | supervisor id, pid |
| Duplicate supervisor blocked | WARNING | existing supervisor id, lease expiry |
| Worker started | INFO | worker name, pid, command fingerprint |
| Worker exited unexpectedly | ERROR | worker name, pid, restart count |
| Capital.com 429 | WARNING | endpoint class, retry time |
| Prediction started/completed | INFO | run id, model version, symbol, resolution |
| Prediction failed | ERROR | run id, model version, error |
| Validation completed | INFO | run id, wins, losses, pending |
| Shadow status updated | INFO | active run id, shadow model version, status |
| Promotion evaluated | INFO | model version, final status, failed gates |
| Dataset snapshot created | INFO | dataset id, checksum, row count |
| Walk-forward experiment completed | INFO | experiment id, windows, summary metrics |

### 7.3 Heartbeat Status Values

| Status | Meaning |
|---|---|
| `OK` | Worker operating normally |
| `STALE` | Derived dashboard state when heartbeat is too old |
| `ERROR` | Worker encountered a non-rate-limit failure |
| `COOLDOWN` | Worker paused due to rate-limit/backoff |
| `MISSING` | No heartbeat row exists |
| `DISABLED` | Worker intentionally disabled by config |

### 7.4 Failure Recovery

- On subprocess failure, caller SHALL capture stdout/stderr tail and write it to logs and status details.
- On database write failure after artifact generation, the command SHALL mark heartbeat `ERROR` and retain artifact paths for manual recovery.
- On Capital.com `429`, workers SHALL update `api_rate_limit_state`, set heartbeat `COOLDOWN`, and skip affected work until `retry_after_utc`.
- On duplicate supervisor detection, startup SHALL exit without starting new workers.

## 10. Acceptance Criteria

- All scoring outputs are produced by one canonical scorer.
- Active and shadow signals show independent `PENDING/WIN/LOSS` status.
- Model performance API exposes active-vs-shadow lift, disagreement rate, and horizon-specific metrics.
- Candidate model promotion requires multi-gate approval.
- Dataset snapshots prevent train/evaluation overlap.
- Walk-forward backtests compare candidate, active, and baselines on identical windows.
- Duplicate worker stacks are prevented by default.
- Capital.com rate limits produce `COOLDOWN`, not repeated worker `ERROR`.
- Every prediction run has a persisted data quality report.
- Dashboard actions operate on explicit selected run/symbol/resolution and surface backend failures.
